// @overview
Core information model of openEHR: EHR structure, demographic model, data types, data structures, common versioning and audit structures, and the EHR Extract model. Archetypes constrain RM instances to express domain content.

// @spec:support
Foundation package of the Reference Model. Defines assumed types, external terminology references, version identifiers, and measurement information shared by all other RM packages. It includes terminology-related definitions for referencing external terminologies such as SNOMED CT, LOINC, and openEHR's own terminology within RM instances. Implementers building any openEHR service layer will use the types defined here for version control, audit trails, and measurement unit handling.

// @spec:data_types
Complete set of clinical and administrative data types: quantities with units and precision, coded text, plain text, date and time representations, proportions, encapsulated media content, and URIs. The type hierarchy is designed to cover clinical documentation requirements without being domain-specific, enabling archetype authors to constrain them to particular use cases. Key types include DV_QUANTITY for measured values with units, DV_CODED_TEXT for terminology-bound concepts, and DV_DATE_TIME for temporal data.

// @spec:data_structures
Generic structural types used throughout the Reference Model: single items, lists, tables, and trees, each parameterised to hold any RM data type instance. ITEM_TREE, ITEM_LIST, ITEM_TABLE, and ITEM_SINGLE are the four structural types, parameterised with ELEMENT as the leaf value holder. Archetypes impose specific structural constraints on these types to define the shape of data captured in clinical entries.

// @spec:common
Cross-cutting Reference Model constructs: the archetyped class hierarchy, entry metadata, feeder audit for legacy data, party references, change control, version containers, and directory structures. The LOCATABLE class and its archetyped subclass form the root of the constraint hierarchy that archetypes act upon, making this package central to understanding how archetypes bind to RM instances. The VERSIONED_OBJECT and VERSION classes implement an optimistic locking model for EHR content, supporting concurrent access and merge scenarios.

// @spec:ehr
Core model of the openEHR Electronic Health Record. Specifies the top-level EHR structure, Composition as the unit of clinical documentation, and the entry hierarchy covering observations, evaluations, instructions, and actions. EHR_STATUS carries subject identity and access control metadata, while COMPOSITION represents a clinically committed unit of information contributed by a care episode. The entry hierarchy - OBSERVATION, EVALUATION, INSTRUCTION, ACTION - maps to the main clinical documentation intents and is the primary target of archetype constraints.

// @spec:demographic
Information model for parties and their relationships: persons, organisations, roles, identity types, contact details, and party relationships. Designed for use alongside or independently of the EHR. PARTY_SELF, PARTY_RELATED, and PARTY_IDENTIFIED provide progressively richer representations of subjects referenced in EHR entries. The model is intentionally generic, allowing it to serve as a standalone demographic service or to be referenced from within EHR content.

// @spec:ehr_extract
Model for packaging and exchanging structured subsets of an EHR between systems, supporting query-driven extraction, synchronisation-based transfer, and discharge summary scenarios. The model supports both full and partial extracts, including the ability to filter by care episode, date range, archetype, or composition type. It is used in discharge summary exchange, patient summary transfer, and cross-institutional record sharing scenarios.

// @spec:integration
Structures for incorporating legacy or non-archetyped clinical content into an openEHR EHR. Provides a bridge representation enabling incremental migration of existing data from external systems. The GENERIC_ENTRY class carries data that cannot yet be expressed in archetypes, allowing legacy content to coexist with fully archetyped data in the same EHR. This approach supports phased migration strategies where systems incrementally replace legacy data representations with properly constrained archetype-based content.
